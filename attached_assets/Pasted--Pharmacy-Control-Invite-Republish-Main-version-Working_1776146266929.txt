Complete Email System Blueprint — 17 Email Flows
Architecture Overview
Email Provider: SendGrid (@sendgrid/mail) Deduplication: Custom checkEmailDedup() service prevents duplicate sends within X minutes SMS Companion: Optional Twilio SMS sent alongside patient-facing emails Logging: Every email send (success or failure) logged to system_logs table Demo Mode: If SENDGRID_API_KEY is not set, emails are logged but not sent Auth: Internal endpoints protected by x-internal-api-key header; admin endpoints by session auth

Environment Variables Required
SENDGRID_API_KEY          - SendGrid API key
SENDGRID_FROM_EMAIL       - From address (e.g., support@yourapp.com)
SENDGRID_FROM_NAME        - From display name (e.g., "Your App Portal")
INTERNAL_API_KEY          - Shared secret for server-to-server email calls
NEXT_PUBLIC_SITE_URL      - App URL (e.g., https://app.yourapp.com)
ADMIN_ALERT_EMAIL         - Admin email for alert notifications

Shared Patterns Across All Emails
Every email has both text (plain text) and html (styled HTML) versions
HTML uses table-based layout for email client compatibility (600px max width)
Header: gradient background with logo + title
Footer: copyright line with current year
All user-supplied strings are HTML-escaped via escapeHtml() to prevent XSS
Every send is wrapped in try/catch — email failures never crash the parent operation
EMAIL #1: MFA Verification Code
File: core/services/mfa/mfaService.ts Function: sendMFACode(userId, email) Endpoint: Not an API route — called directly from auth flow Subject: "Your Verification Code" To: The user logging in Triggered by: User enters correct password → MFA code generated and emailed

How it works:
Generate random 6-digit code
Invalidate any previous unused codes for this user (UPDATE mfa_codes SET is_used = true WHERE user_id = X AND is_used = false)
Store new code in mfa_codes table with 10-minute expiry
Send email with large styled code display
User enters code on MFA verify page → verifyMFACode() checks it
Key details:
Code expires in 10 minutes
Max 5 failed attempts before 15-minute lockout
Failed attempts tracked in mfa_verification_attempts table
Lockout check runs before code validation
Email content:
Large monospace code in a blue gradient box (font-size: 40px, letter-spacing: 12px)
Warning: "This code expires in 10 minutes. Do not share this code with anyone."
Security notice section at bottom
Database tables needed:
mfa_codes (id, user_id, code, expires_at, is_used, created_at)
mfa_verification_attempts (user_id, failed_attempts, locked_until, last_failed_at)
EMAIL #2: Password Reset
File: app/api/auth/send-reset-email/route.ts Method: POST Subject: "Reset Your Password" To: User requesting reset Triggered by: User clicks "Forgot Password" on login page

How it works:
Receive email from request body
Use Supabase admin to generate a recovery link: supabase.auth.admin.generateLink({ type: "recovery", email, options: { redirectTo } })
Extract hashed_token from the link data
Build reset URL: ${SITE_URL}/auth/confirm?token_hash=${tokenHash}&type=recovery
Send email with "Reset Password" button linking to that URL
Key details:
Link expires in 1 hour
Always returns { success: true } even if email not found (prevents user enumeration)
No deduplication — users can request multiple resets
Email content:
Blue gradient header with "Reset Your Password"
"Reset Password" CTA button
Warning: "This link expires in 1 hour"
Security notice: "AIM RX will never ask for your password via phone or text"
EMAIL #3: Provider Welcome (Invite Doctor)
File: app/api/admin/invite-doctor/route.ts Method: POST Subject: "Welcome to [App Name] - Your Provider Account" To: Newly invited doctor Triggered by: Admin clicks "Invite Doctor" in admin panel Auth: Requires admin or super_admin role

How it works:
Admin fills in doctor details (name, email, password, NPI, license, etc.)
Create Supabase auth user with email_confirm: true (pre-verified)
Create user_roles record with role = "provider"
Create providers record with all profile data, is_active: false
If companyName provided, sync to group patients via RPC
Send welcome email with login credentials
Key details:
If auth user creation fails (duplicate email), clean up and return error
If role creation fails, delete auth user
If provider record fails, delete role and auth user (cascade cleanup)
Provider starts inactive — must complete profile before activation
Email send failure does NOT fail the entire request
Email content:
Gradient header with logo + "Welcome to [App Name]"
Login credentials box: Portal URL, Email, Temporary Password (in <code> tag)
Next steps checklist (numbered): Log in, complete profile, enter NPI, add addresses, change password
Security warning: change temporary password immediately
Account activation notice: team will review NPI and credentials

EMAIL #15: Admin Alert — Unknown DigitalRx Status
File: core/services/admin-alerts.ts Function: alertUnknownDigitalRxStatus(patientName, medication, queueId, prescriptionId, rawStatus, rawData) Subject: "[App Name WARNING] Unknown DigitalRx Status '[status]' — [Patient Name]" To: Admin alert email Triggered by: digitalrx-reconcile.ts cron job — when pharmacy sends unrecognized status

How it works:
Cron job polls pharmacy API for order statuses
If a status doesn't match known statuses (submitted, processing, approved, packed, shipped, delivered, etc.)
Call alertUnknownDigitalRxStatus() which calls the generic sendAdminAlert()
Email includes raw API response (truncated to 300 chars)
Email content:
Compact admin-style email (not patient-facing)
WARNING badge (yellow) or CRITICAL badge (red)
Headline: "DigitalRx returned an unrecognized status: '[status]'"
Info box: Patient name, Medication, Queue ID, Prescription ID
Details list:
"The system received a status it doesn't recognize"
"Contact the pharmacy to verify the order status"
Raw API response snippet
Footer: "Log in to [app URL] to take action"
EMAIL #16: Admin Alert — Stuck Order
File: core/services/admin-alerts.ts Function: alertStuckOrder(patientName, medication, queueId, prescriptionId, stuckSinceHours) Subject: "[App Name WARNING/CRITICAL] Order Stuck [X]+ Hours — [Patient Name]" To: Admin alert email Triggered by: webhook-monitor.ts and digitalrx-reconcile.ts cron jobs

How it works:
Cron jobs check for prescriptions with status "submitted" that haven't changed in X hours
If stuck > threshold, call alertStuckOrder()
Severity: "warning" if < 72 hours, "critical" if >= 72 hours
Email content:
Same admin alert template as #15
Headline: "Prescription stuck in 'submitted' for [X] hours"
Details:
"This order was submitted but has not progressed"
"No status change detected after [X] hours"
"Check with the pharmacy to confirm they received and are processing this order"
EMAIL #17: Admin Alert — Invalid Tracking Number
File: core/services/admin-alerts.ts Function: alertBadTrackingNumber(patientName, medication, trackingNumber, prescriptionId, reason) Subject: "[App Name CRITICAL] Invalid Tracking Number — [Patient Name]" To: Admin alert email Triggered by: tracking-reconcile.ts cron job Severity: Always "critical"

How it works:
Tracking reconcile cron tries to validate tracking numbers via EasyPost
If carrier can't be identified, call alertBadTrackingNumber()
Patient is NOT notified about shipping until tracking is valid
Email content:
Same admin alert template
CRITICAL badge (red)
Headline: "Tracking number '[number]' is not valid"
Details:
Specific reason for failure
"EasyPost could not identify a carrier"
"The patient has NOT been notified about shipping yet"
"Verify the tracking number with the pharmacy"
