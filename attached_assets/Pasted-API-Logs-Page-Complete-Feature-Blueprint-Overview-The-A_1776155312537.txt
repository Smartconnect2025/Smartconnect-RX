API & Logs Page — Complete Feature Blueprint
Overview
The API & Logs page (/admin/api-logs) is the system health monitoring and patient communication dashboard. It consists of 6 collapsible sections:

Quick Stats Dashboard — 4 summary cards
System Insights — Auto-detected issues with severity, timeline, impact, action steps
API Status Details — Health check results grouped by category
Webhook Activity — DigitalRx webhook event log
Patient Communications — Complete email/SMS send log
Recent Activity — Full system_logs feed with search/filter
Recent Prescriptions — Last 20 prescriptions quick view
Plus a footer with branding and contact info.

PART 2: DATA LOADING
loadAllData() fetches 4 data sources in parallel:
1. Health Data
GET /api/admin/api-health

Returns: { success, overallStatus, healthChecks[], summary: { total, operational, degraded, error } }

2. System Logs (two parallel queries merged)
-- Query A: Last 50 system_logs (all types)
SELECT * FROM system_logs ORDER BY created_at DESC LIMIT 50
-- Query B: Last 50 patient communication logs specifically
SELECT * FROM system_logs
WHERE action IN ('PATIENT_NOTIFICATION_SENT', 'PATIENT_NOTIFICATION_FAILED', 'PATIENT_SMS_SENT', 'PATIENT_SMS_FAILED')
ORDER BY created_at DESC LIMIT 50

Merge logic: Combines both result sets, deduplicates by id, sorts by created_at DESC.

3. Recent Prescriptions
SELECT id, queue_id, submitted_at, medication, dosage, status,
       patient:patients(first_name, last_name)
FROM prescriptions
ORDER BY submitted_at DESC LIMIT 20

Filters out test patients with last_name in ["harton"] (case-insensitive).

4. Prescription Stats
SELECT submitted_at FROM prescriptions

Counts: today (since midnight), this week (last 7 days), all time.

PART 6: API HEALTH ENDPOINT
Route: GET /api/admin/api-health
File: app/api/admin/api-health/route.ts
Auth: Admin role only (checked via user_roles table)

Health Checks Performed:
1. Supabase Database
Method: SELECT count FROM pharmacies
Category: database
Status: operational if no error, else error
2. H2H DigitalRx API
Method: GET {DIGITALRX_BASE_URL}/health with Bearer token
Timeout: 5 seconds
Category: external
Status: operational if HTTP OK, "degraded" (not error) on failure — intentionally soft to avoid false alarms
Default URL: https://www.dbswebserver.com/DBSRestApi/API
3. Stripe Payment API (DISABLED in current deployment)
Commented out — can be re-enabled if Stripe is used
4. Twilio Messaging API (DISABLED in current deployment)
Commented out — can be re-enabled if Twilio is configured
5. Internal API Routes (4 endpoints)
All marked as "operational" since they're on the same server:

Prescription Submit API: /api/prescriptions/submit
Patient Creation API: /api/basic-emr/patients
Medication Catalog API: /api/medication-catalog
Provider Pharmacy API: /api/provider/pharmacy
Overall Status Calculation
Excludes "H2H DigitalRx API" from core status:

If any core API has error → overall = "critical"
If any core API has degraded → overall = "degraded"
Otherwise → "operational"

PART 9: HOW COMMUNICATION LOGS ARE CREATED
Every email/SMS endpoint logs to system_logs after sending. Here's the complete mapping:

Email Types That Create Communication Logs
1. Payment Request Email
API: POST /api/payments/send-payment-email
Trigger: Admin clicks "Send Payment Link" in prescription detail modal
Auth: x-internal-api-key header
Log action: PATIENT_NOTIFICATION_SENT
Log details format: Payment Request Email | To: {email} | Medication: {medication} | Amount: ${totalAmount} | Provider: {providerName}
Subject line: "Action Needed: Complete Payment for Your {medication} Prescription"
Supports multi-medication: Yes — medications[] array with individual names/prices
Email dedup: 30-minute window per payment token
2. Payment Confirmation Email
API: POST /api/payments/send-confirmation-email
Trigger: After successful payment (mark-paid or online payment)
Auth: x-internal-api-key header
Log action: PATIENT_NOTIFICATION_SENT
Log details format: Payment Confirmation Email | To: {email} | Medication: {medication} | Amount: ${totalAmount} | Transaction: {transactionId} | Provider: {providerName}
Subject line: "Payment Confirmed: {medication} Prescription"
Supports multi-medication: Yes — lists each med with price + shipping subtotal
Shows breakdown: Medications Subtotal, Shipping & Handling, Oversight & Monitoring Fees, Total
Email dedup: 30-minute window per transaction ID
3. Status Update Email
API: POST /api/payments/send-status-email
Trigger: Admin override, webhook status update, tracking sync
Auth: x-internal-api-key header
Log action: PATIENT_NOTIFICATION_SENT
Log details format: {subject} | To: {email} | Medication: {medication} | Provider: {providerName} | Pharmacy: {pharmacyName} | Status: {statusType} | Tracking: {trackingNumber} | Rx: {prescriptionId}
Status types and subjects:
pharmacy_processing → "Prescription Update: {medication} Is Being Prepared"
shipped → "Your {medication} Prescription Has Shipped!"
delivered → "Delivery Confirmed: {medication} Prescription"
ready_for_pickup → "Your {medication} Prescription Is Ready for Pickup"
Email dedup: 60-minute window per prescription ID + status type
4. SMS Notifications (parallel to emails)
Each email endpoint also sends an SMS if:

patientPhone is provided in the request body
isSmsConfigured() returns true (Twilio credentials exist)
SMS log actions:

PATIENT_SMS_SENT — success
PATIENT_SMS_FAILED — failure
SMS log details format mirrors email but says "SMS" instead:

Payment Request SMS | To: {phone} | Medication: {medication} | Amount: ${amount} | Provider: {provider}

PART 10: EMAIL DEDUPLICATION GUARD
File: core/services/email-guard.ts
Function: checkEmailDedup(recipientEmail, emailType, deduplicationKey, windowMinutes)
Returns: { allowed: boolean, reason?: string }

Three-layer protection:
Layer 1: Exact Duplicate Check
SELECT id FROM system_logs
WHERE user_email = {recipientEmail}
  AND action = 'PATIENT_NOTIFICATION_SENT'
  AND details ILIKE '%{deduplicationKey}%'
  AND details ILIKE '%{emailType}%'
  AND created_at >= {windowStart}
LIMIT 1

If found → blocked (duplicate within window).

Layer 2: Hourly Rate Limit
SELECT COUNT(*) FROM system_logs
WHERE action = 'PATIENT_NOTIFICATION_SENT'
  AND created_at >= {1 hour ago}

If count ≥ 100 → blocked (hourly cap).

Layer 3: Daily Rate Limit
SELECT COUNT(*) FROM system_logs
WHERE action = 'PATIENT_NOTIFICATION_SENT'
  AND created_at >= {24 hours ago}

If count ≥ 500 → blocked (daily cap).

Fail-open: If any check throws an error, returns { allowed: true } (doesn't block).

PART 16: SYSTEM_LOGS TABLE — ACTIONS REFERENCE
All communication-related actions logged to system_logs:

Action	Meaning	Logged By
PATIENT_NOTIFICATION_SENT	Email sent successfully	send-payment-email, send-confirmation-email, send-status-email
PATIENT_NOTIFICATION_FAILED	Email send failed	send-payment-email, send-confirmation-email, send-status-email
PATIENT_SMS_SENT	SMS sent successfully	All email routes (when phone + Twilio configured)
PATIENT_SMS_FAILED	SMS send failed	All email routes (when phone + Twilio configured)
WEBHOOK_STATUS_UPDATE	Pharmacy webhook received	webhook/digitalrx route
WEBHOOK_*	Any webhook event	Various webhook handlers
ADMIN_PRESCRIPTION_OVERRIDE	Admin manual status change	admin-override route
ADDRESS_UPDATED	Shipping address changed	update-address route
Log Fields Used by Patient Communications UI:
user_email — recipient email or phone number
user_name — patient name
details — pipe-delimited string parsed for display (type | To: | Medication: | Provider: | Pharmacy: | Tracking: | Amount:)
action — determines whether it shows as email, SMS, success, or failure
status — "success" or "error"
created_at — timestamp for display and sorting
