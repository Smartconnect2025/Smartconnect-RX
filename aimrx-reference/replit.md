# AimRX - Pharmacy Management Portal

## Overview
AimRX is a healthcare/pharmacy management application (AIM Rx Portal) built with Next.js 15. Its primary purpose is to empower healthcare providers to efficiently manage patients, create and submit prescriptions to compounding pharmacies, and handle patient billing. The project aims to streamline the prescription workflow, enhance patient care through better medication management, and provide robust administrative and reporting capabilities for pharmacy operations.

## System Architecture
The application is built on Next.js 15.4.10 using React 19 and TypeScript, styled with Tailwind CSS v4 and ShadCN UI (Radix UI). Data persistence is handled by Supabase (PostgreSQL) with Drizzle ORM, and state management is done with Zustand. Form handling utilizes React Hook Form with Zod validation. Authentication is managed by Supabase Auth, implementing role-based access control and custom multi-factor authentication (MFA).

The system features several core functionalities:
- **Patient Management (Basic EMR):** Allows providers to manage patient information and encounters.
- **Prescription Workflow:** Enables creation, submission, and tracking of prescriptions to compounding pharmacies, including DEA number integration and DigitalRx payload alignment.
- **Medication Management:** Comprehensive patient medication tab displaying both ordered prescriptions and manually tracked medications, with detailed views and search/filter capabilities.
- **Provider Product Catalog:** A dedicated browsable catalog for providers to view available products, including search, filter, sort, and detailed product information with tier discounts.
- **Admin Dashboards:** Dedicated dashboards for administrators to manage categories, providers, groups, and access detailed reporting and analytics.
- **Reporting & Analytics:** Interactive dashboards with Recharts visualizations (revenue trends, order status, top providers, pharmacy comparisons) and key performance indicator (KPI) cards.
- **Group Management:** Functionality for assigning providers to groups, filtering, and performance tracking.
- **Shipment Tracking:** Integration with EasyPost for real-time prescription shipment tracking, including webhooks and cron jobs for reconciliation.

Architectural decisions include:
- **Modular Feature Development:** The application is structured with self-contained feature modules (e.g., `admin-dashboard`, `basic-emr`, `provider-dashboard`).
- **API-Driven:** Extensive use of API routes for server-side logic and data interaction.
- **Role-Based Access Control:** Implemented for secure access to different parts of the application, ensuring only authorized users can perform specific actions.
- **Robust Authentication:** Supabase Auth with custom MFA, including fixes for potential redirect loops and enhanced security measures.
- **UI/UX:** Uses ShadCN UI for a consistent design system, with components like interactive charts, status badges, and collapsible panels for an improved user experience.
- **Database Management:** Raw Supabase JS client + direct psql via `$SUPABASE_DATABASE_URL`. Drizzle is **NOT** used — do not add Drizzle imports. There is no `db:push` script — schema changes go through psql migrations. (Hard rule, established post-Greenwich/Rahmany incident May 2026.)
- **DigitalRx Reconcile Cron — RULE: NEVER POLL TEST PATIENTS** (`core/cron/jobs/digitalrx-reconcile.ts`). The every-4-hours America/Chicago reconcile job (schedule `0 */4 * * *`, bumped from once-daily 6PM CT on May 11 2026 after the Joseph Phillipine q2232883 incident — 54-hour limbo because Greenwich never fired a webhook AND their status-poll API was returning non-JSON, so we missed our once-daily window twice in a row) uses an `isTestPatient()` helper that excludes any patient whose name contains `\btest`, whose name is `aimrx`, whose email matches a word-boundary `test`, whose email starts with `aimrx`, or whose email matches `^joseph\+.*@smartconnects\.com$`. Test patient IDs are resolved up front and excluded at the SQL level via `.not("patient_id", "in", ...)` so stale test queue_ids never crowd real patients out of the 50-row poll window. This rule was established May 4 2026 after stale test queue_ids were producing 30–150 daily DigitalRx error logs. (Joseph: "make a rule and we push that rule never do the test paitnets ever")
- **Trusted Device — multi-user cookie format (Step 11, May 2026):** The `aimrx_td` cookie value is a **period-separated list** of trust tokens (e.g. `tokA.tokB.tokC`), capped at `MAX_TRUST_TOKENS = 5` with FIFO eviction. Period is outside the base64url alphabet so splitting is unambiguous. Legacy single-token cookies (no period) decode to a one-element list and keep working. Each token in the list is owned by a different user — when account B trusts the same browser already trusted by account A, account B's token is **appended**, not substituted, so signing back in to account A still skips 2FA. Always read the cookie via `decodeTrustTokenList()` and write it via `encodeTrustTokenList()` from `core/auth/trusted-device.ts`. Never assume a single-token cookie. The Step 10 scrubber regex (`[A-Za-z0-9_-]{43}` with non-base64url word boundaries) handles the new format because period is a non-base64url char — but every new code path that touches the cookie must still be reviewed against the leak checker.
- **Trusted Device — per-user cap of 10 (Step 12, May 2026):** `MAX_TRUSTED_DEVICES_PER_USER = 10` in `core/auth/trusted-device.ts`. Internal `enforceTrustedDeviceCap(userId)` runs after every fresh GRANT (both `fresh_insert` and `vanished_retry_insert` paths in `createTrustedDevice`) and FIFO-evicts the oldest active rows past the cap via `revokeTrustedDevice(..., { reason: "cap_exceeded" })`. NOT wired into rotation/refresh paths (no new row count). Helper has its own try/catch — cap-enforcement failure must NEVER break the MFA flow. Per-evict audit row goes to `system_logs` automatically through the existing revoke path.
- **Trusted Device — new-trust email notification (Step 13, May 2026):** `core/services/trusted-device-email.ts` → `sendNewTrustedDeviceEmail()` is called fire-and-forget (`void`) after both new-row paths in `createTrustedDevice`. Recipient is resolved via `supabase.auth.admin.getUserById(userId)` and is **always and only the account owner** — never admins, never other providers, never patients. Body contains UA-derived browser label, IP, and America/Chicago time; **NO** raw fingerprint, **NO** token. SendGrid not configured = silent skip (so dev grants don't spam logs). Errors run through `scrubError()` (Step 10 leak guard) in case the SendGrid SDK ever surfaces a request body.
- **Trusted Device — nightly cleanup cron (Step 14, May 2026):** `core/cron/jobs/trusted-devices-cleanup.ts` runs daily at 3:00 AM America/Chicago. Hard-deletes rows from `trusted_devices` where `revoked_at < now() - 30 days` OR (revoked_at IS NULL AND `expires_at < now() - 30 days`). 30-day buffer is intentional so support can still answer "what device was on my account last week." Uses select-then-delete-by-id (never a blind WHERE-only DELETE) so anomalies are visible in `cron_job_runs.details` (purged_count, sample_ids, retention_days, cutoff). The permanent grant/use/revoke history lives in `system_logs` (Step 9) and is **never touched** by this cron — only the live state table shrinks. Has `isRunning` re-entrancy guard.
- **Trusted Device — never log raw token (HARD HIPAA RULE, May 2026):** The raw `aimrx_td` cookie value, the trust token returned by `crypto.randomBytes(32).toString("base64url")`, and the raw device fingerprint **MUST NEVER** appear in `system_logs`, console output, error messages, thrown `Error` objects, or future Sentry events. Only the SHA-256 `token_hash` and the SHA-256 `fingerprint_hash` may be persisted. Any code path that stringifies an unknown error or arbitrary value into a logger MUST run it through `scrubError()` / `scrubTrustToken()` from `core/auth/scrub-trust-token.ts`. A static checker (`scripts/verify-no-trust-token-leak.ts`) scans the trusted-device files for risky patterns. A forward-compatible Sentry `beforeSend` scrubber lives at `core/observability/sentry-scrubber.ts` ready for the day Sentry is wired in. (Step 10 of 14-step Trusted Device feature.)
- **Greenwich Rx PDF generator:** `utils/generatePrescriptionPdf.ts` renders the visual Greenwich Electronic Rx template (outer frame, NPI/SPI/DEA/Effective header, framed Rx box, Generic Substitution / Sub. Allowed / Notes row, Signed electronically by + PON footer). New optional `PrescriptionPdfData` fields (`dea`, `spi`, `effective`, `fax`, `companyName`, `daysSupply`, `pon`) render blank when absent. PON is derived from `prescription.id.slice(-8).toUpperCase()` by callers (`app/(features)/prescriptions/new/step3/page.tsx` and `core/cron/jobs/refill-check.ts`). DB-absent fields (SPI, fax, effective date) intentionally render as empty labels.
- **Payment Reconciliation — every-1-minute primary safety net (May 7 2026, Keith Robinson incident):** `core/cron/jobs/payment-reconcile.ts` is scheduled `* * * * *` (every 60 seconds) in `core/cron/index.ts`. This cron — NOT the AuthNet webhook — is the authoritative path that flips `payment_transactions.payment_status` from `pending`/`processing` to `completed`. The webhook at `/api/webhooks/authnet` is treated as a speed optimization only; if `AUTHNET_SIGNATURE_KEY` is missing in Render prod or the webhook URL is misconfigured at the AuthNet portal, payments STILL confirm automatically within 60 seconds. The reconciler has: (1) `isRunning` re-entrancy guard so overlapping ticks are skipped, (2) scans ALL pending/processing rows (no longer filters out NULL `authnet_ref_id`), (3) primary match by `invoiceNumber=authnet_ref_id`, (4) FALLBACK match by amount-to-the-cent + `submitTimeUTC` within 24h AND after `created_at`, greedy first-come for collision safety, each AuthNet txn matches at most one row, (5) suppresses empty-tick `system_logs` writes (1,440 ticks/day would otherwise drown the audit trail). Patient-facing success page (`app/(features)/payment/success/[token]/page.tsx`) polls for 5 min (`MAX_POLLS=300`) then shows a calm blue "Thank You" state — never the alarming yellow "contact support" screen. **Hard rule: do NOT re-add AuthNet webhook config as a hard dependency.** The reconciler must remain self-sufficient.
- **Greenwich always uses generated PDF — Step 1 upload override (May 7 2026, Trevor Haynes "wrong PDF" incident):** Step 1 of the new-prescription flow (`app/(features)/prescriptions/new/step1/page.tsx`) has an OPTIONAL "Prescription Document" file picker that stores any uploaded file in `sessionStorage["prescriptionPdfData"]`. Step 3 (`app/(features)/prescriptions/new/step3/page.tsx`) historically PREFERRED that uploaded file over the system-generated Electronic Rx PDF. For Greenwich orders this is fatal: their pharmacists need the structured Electronic Rx layout (NPI/SPI/DEA header, framed Rx box, "AIM" drug-name prefix, PON) and reject/queue user scans, phone photos, or foreign Rx templates ("NO RX IMAGE" / "WRONG FORMAT"). Trevor Haynes's only 2 Greenwich submissions (Sunny Haynes q2226003 5/7 + Amanda Chase q2198891 5/5) both reached Greenwich as 74-124KB JPEG-in-PDF wrappers because his Step 1 upload was honored. **Hard rule in step3:** `const isGreenwichItem = isGreenwichPharmacy(item.selectedPharmacyId); let pdfToUpload = isGreenwichItem ? null : pdfInfo;` — for Greenwich, the user-uploaded file is ALWAYS discarded and the system regenerates fresh from `generatePrescriptionPdf`. Non-Greenwich pharmacies still honor uploaded PDFs (back-compat). Do NOT remove this gate. Do NOT add new code paths that send user-uploaded files to Greenwich.
- **PDF availability wait — submit-to-pharmacy-core (May 7 2026, Greenwich "NO RX IMAGE ATTACHED" incident):** The frontend (`app/(features)/prescriptions/new/step3/page.tsx`) calls `/api/prescriptions/submit` FIRST and uploads the PDF to `/api/prescriptions/[id]/pdf` 1-2 seconds LATER. For pay-on-terms providers, `submit/route.ts` auto-fires `mark-paid` → `submit-to-pharmacy-core` in-process — racing ahead of the parallel PDF upload. Result (May 4-7): 7 of 29 submissions reached Greenwich with NO PDF, sitting in their queue tagged "NO RX IMAGE ATTACHED" for days. **Fix in `app/api/prescriptions/_shared/submit-to-pharmacy-core.ts`:** before the PDF freshness check, if `prescription.pdf_storage_path` is empty, poll the row every 500ms for up to 8s waiting for the upload to land. On hit, mutate the in-memory prescription and log `step=pdf-wait-resolved`. On timeout, log `PRESCRIPTION_SUBMIT_PDF_WAIT_TIMEOUT` and proceed without PDF (keeps the "ship even if image is missing" policy). **Hard rule: do NOT remove this wait. Do NOT call `submit-to-pharmacy-core` from any new path until you've confirmed the PDF is uploaded — the wait is a safety net, not a license to add new races.** Bonus fix in same commit: the pdf-download step was using `prescription.pdf_storage_path` (original) instead of `effectivePdfPath` (post-regenerate), so stale-PDF auto-regeneration was downloading the OLD path. Switched to `effectivePdfPath`.
- **Greenwich PDF health badge — three-class detector (May 8 2026, Joseph clarification):** The Admin Incoming Queue green/red badge under Queue ID covers ALL three Greenwich-PDF failure modes, not just size. Detector lives in `app/api/admin/prescriptions/route.ts` `computePdfHealth()` and returns `{state, reason}`; tooltip in `app/(features)/admin/prescriptions/page.tsx` renders a human-readable explanation per reason code. Three classes: **(1) size** — PDF in storage <200KB (Trevor's image-only JPEG-in-PDF wrappers). **(2) race** — `pdf_push_confirmed_at IS NULL` on submitted+ rows (Wicks/Welzel/Vogt/Province/Polansky/Lee/Landow/Harr/Koch/Paesani — 1.2-1.5MB on our side but Greenwich never received them because submit fired before upload finished). The column is written by `app/api/prescriptions/_shared/submit-to-pharmacy-core.ts` after the success update ONLY when `pdfBase64` was non-null in the DigitalRx request body — never speculatively. **(3) content** — `pdf_validation_error IS NOT NULL` (Robinson: 2.83MB PDF whose drug name lacked the "AIM " prefix because the prescription had no catalog `medication_id`, so `useGreenwichFormat` fell through to false). Validation runs in `core/services/regenerate-stale-pdf.ts` `regenerateGreenwichPdfFromRow()` after a successful upload; missing `catalogDrugName` → `no_catalog_aim_prefix`, missing patient name → `patient_name_missing`. The column is ALWAYS written (null on success) so a fixed re-regen clears the badge. **Joseph's "any layer fails = red" rule:** storage-lookup failures now return `bad` (was previously degraded to `na` — that hid the problem). Migration `core/database/migrations/20260508120000_pdf_health_tracking.sql` adds the two columns AND backfills `pdf_push_confirmed_at` for every existing Greenwich submitted+ row (set to `COALESCE(submitted_to_pharmacy_at, submitted_at, updated_at, now())`) so historical orders default to green. Only NEW submissions going forward use the strict "no confirmation = red" rule. The 10 known historical race victims are tracked separately for resend (follow-up task). **Hard rule:** do NOT add new code paths that flip these fields without going through the documented writers above. Do NOT add a non-bad fallback for storage-lookup failure — Joseph's rule overrides "transient blip is fine" thinking.
- **Greenwich PDF self-healing — server-side health check (May 8 2026, Trevor Haynes incident):** `app/api/prescriptions/_shared/submit-to-pharmacy-core.ts` runs `ensureHealthyGreenwichPdf()` (from `core/services/regenerate-stale-pdf.ts`) for every Greenwich submission AFTER the existing Step-1 client override and the pre-May-1 freshness regenerator. If the storage object is missing OR smaller than `HEALTHY_PDF_MIN_BYTES = 200_000`, it force-regenerates from `generatePrescriptionPdf` and overwrites `pdf_storage_path`. **HARD RULE from Joseph (voice-of-the-CEO, May 8 2026):** *"if it is red you see it INTERNALLY and fix and send it green always ... nothing stopps the order ... lives of people we are dealing with."* The health check is fully non-blocking — wrapped in try/catch, even total regen failure logs `PRESCRIPTION_PDF_HEAL_FAILED` and PROCEEDS with whatever PDF exists. The order ALWAYS goes out. The 200KB threshold is calibrated against the bug pattern (Trevor's image-only JPEG-in-PDF wrappers were 73-124KB; every legitimate Electronic Rx is ≥593KB, smallest legit being Daniel Omire Mayor at 593KB). Admin Incoming Queue table (`app/(features)/admin/prescriptions/page.tsx`) shows a green `PDF ✓` badge under Queue ID for every healthy Greenwich submission (data sourced via `/api/admin/prescriptions` batch storage.objects size lookup). A red `PDF !` badge means auto-heal failed AND order shipped anyway — that is a real bug to chase, not a customer-facing block. Do NOT add an `exitFailure` path to the health check. Do NOT expose any "PDF rejected, please re-upload" UI to providers. Do NOT remove the badge — it is the visible proof that every Greenwich submission has a proper Electronic Rx behind it.
- **get-hosted-token authnet_ref_id backfill (May 7 2026):** `app/api/payments/get-hosted-token/route.ts` defensively backfills `authnet_ref_id` if the row is missing one before building the AuthNet hosted-form request. Without this, a row whose `authnet_ref_id` was nulled (support reset, legacy bug, race during re-issue) would create an AuthNet transaction with EMPTY `invoiceNumber` — unfindable by the reconciler's primary matcher. Same 20-char `PAY{base36-time}{4-rand-hex}` format generate-link uses. Also persists the generated id back to the row so the reconciler can match it.
- **DigitalRx reject keyword requires Active_Rx=0 + three writers (Emily Freeman incident, May 28 2026):** THREE code paths can map a Greenwich response to `status='rejected'`: (1) `app/api/prescriptions/_shared/digitalrx-helpers.ts` `mapDigitalRxStatus` — used by the 5-min reconcile cron, (2) `app/api/webhook/digitalrx/route.ts` POST handler — live pharmacy push, (3) `app/api/prescriptions/status-batch/route.ts` — browser-driven polling endpoint hit every time a provider opens Prescriptions or Refills page. The third was the silent killer in Emily's case: it called `mapDigitalRxStatus` (so it inherits any guard there) but wrote status changes with `console.log` only — NO `system_logs` audit row — so a transient reject blip from Greenwich was applied to the DB invisibly. All three paths now enforce an Active_Rx guard: only `"0" | "false" | "no"` (case-insensitive, also matches numeric 0 / boolean false via String()) honors the reject. Truthy / `"1"` / absent → REFUSE: the helper preserves `currentStatus`; the webhook re-derives from the highest-ordinal non-reject signal (workflow token like `Statuswf="typed"` → packed, OR date fields PackDateTime/ApprovedDate/Tracking/Pickup/DeliveredDate, whichever yields a higher STATUS_ORDINAL; falls back to `submitted` only when both absent); status-batch inherits via the helper. **status-batch additionally writes `BATCH_DIGITALRX_STATUS_CHANGED` to `system_logs` on every status flip** (fire-and-forget, never blocks the user's page load) — closing the audit-trail gap. The "rejected always wins" override in `isForwardStatusTransition` (helpers line ~78, webhook line ~171) stays — it's what lets a legitimate Active_Rx=0 reject override a row already at packed/approved, and with the upstream Active_Rx guard it can no longer be triggered by transient blips. Emily Freeman q2404472 (BPC) + q2404478 (NAD+) sat locked as `rejected` for 22h while Greenwich's API returned `Statuswf=TYPED, Active_Rx=1, approveddated` set — orders were being filled the whole time. Webhook never fired ("Last webhook: never" alerts) and reconcile cron logs were empty, so the rejection had to have come from status-batch — confirmed once we mapped all three writers. **Hard rule:** any NEW code path that writes `status='rejected'` to prescriptions must apply the same Active_Rx guard AND log to `system_logs`. The only legitimate non-guarded writer is `app/api/payments/refund-partial/route.ts` (admin refund — orthogonal to pharmacy status). **Forensic rule:** if a prescription's status changes with no audit row, a NEW unguarded silent writer was added — find and guard it.
- **Pre-payment prescriber validator — DEA NOT required (May 9 2026, Joseph clarification):** `core/services/prescriber-credentials.ts` `computeMissingPrescriberFields()` enforces NPI + signature + ≥1 medical license, but **NOT** DEA. AimRx ships peptides + non-controlled compounded meds (BPC-157, KPV, TB-500, etc.); Greenwich accepts these without a DEA in the Electronic Rx, and the real-world supervising provider for the first live assistant flow (Dr. Randolph Whipps, Cather→Whipps delegation) does not carry a DEA on file. Joseph: *"they have all the proper validations to do the orders since they are assistance"*. Re-add DEA as required ONLY when controlled substances are introduced AND the validator can detect controlled-substance line items per-Rx — never as a blanket requirement. The `MissingCredential` union is `"npi" | "signature" | "medicalLicense"` — do NOT re-add `"dea"` to it.
